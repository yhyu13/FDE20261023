### User Story 1 - 素材与运营数据没有变成可检索的场景事实 (Priority: P1)

**业务问题**：申沃的智能驾驶，下一站开向哪里？

**根因**：售后侧虽已有零代码试点，但市场侧的素材仍是视频、里程、接管事件这些非结构化或半结构化资产，只以文件名与口述存在；没有场景标签、没有出处、没有时点

**为什么值得做**："场景化传播"四个字的底座就是场景能不能被检索到；也是"不再每月从零开始"的唯一前提

**Independent Test**: ⚠️ 待补——写清「怎么单独验收这一条」，以及「只实现这一条时交付什么」。

**Acceptance Scenarios**: ⚠️ 待补——Day1 现场按真实业务动作补 Given/When/Then。

### User Story 2 - 讲得出参数，讲不出运营价值 (Priority: P2)

**业务问题**：申沃的智能驾驶，下一站开向哪里？

**根因**：内容停在"自动驾驶 / 激光雷达 / 算力"的概念与技术层；RoboBus 的价值在运营链路（城市线路、车队调度、乘客预约、运营方结果），这条链路没有被翻译成内容语言

**为什么值得做**：讲不出运营价值，RoboBus 就只是一台更贵的车——这正是"下一站"要回答的

**Independent Test**: ⚠️ 待补——写清「怎么单独验收这一条」，以及「只实现这一条时交付什么」。

### User Story 3 - 对外事实没有唯一版本与出处，发布前拦不住 (Priority: P3)

**业务问题**：申沃的智能驾驶，下一站开向哪里？

**根因**：参数、里程、车辆数、接管率散在 PPT、测试报告、同事口述里，版本与时点不明；多端改写靠复制粘贴，口径逐版漂移；合规红线没有可执行清单

**为什么值得做**：一次对外参数错误 = 一次公开事故 + 一次信任损失，而且往往发布后才发现；凡要签字的数字必须可溯源

**Independent Test**: ⚠️ 待补——写清「怎么单独验收这一条」，以及「只实现这一条时交付什么」。

**Acceptance Scenarios**: ⚠️ 待补——Day1 现场按真实业务动作补 Given/When/Then。

### User Story 4 - 内容效果不回流，选题只能凭直觉 (Priority: P4)

**业务问题**：申沃的智能驾驶，下一站开向哪里？

**根因**：发布后各平台数据与内容之间没有绑定，"哪类题材 / 哪个场景有效"没人答得出来；市场部的采纳与弃用意见也没留痕

**为什么值得做**：业务目标第三条是"内容持续运营"——没有回流就没有学习闭环，流水线跑得再快也只是更快地产出无效内容

## Requirements *(mandatory)*

### Functional Requirements

> 每条 FR 来自一条 **L3 机制**，并注明它属于哪个 L2 缺口。
> 凡是**要签字的数字与参数**，FR 必须写明溯源要求；
> 凡是**低置信结果**，FR 必须写明人工确认要求。

- **FR-001**: System MUST 视频抽帧 → VLM 生成场景描述 → 归一为受控标签（天气 / 路段 / 交通参与者 / 车型 / 城市 / 线路 / 是否接管）+ 人工纠正回写
  - 来源：L2 L2-1 / L3 多模态素材场景打标管线
  - 同族复用：任何"素材躺在硬盘"的库：展会演示录像、现场施工照片、培训录像、产品开箱视频
- **FR-002**: System MUST 把测试报告、车队台账、口述补充抽成结构化事实原子 主体 + 指标 + 数值 + 口径 + 时点 + 出处；同名指标只留一条，多条并存显式标"口径分歧"
  - 来源：L2 L2-1 / L3 事实原子抽取与归一
  - 同族复用：财报关键数据抽取、招投标参数归集、质检报告指标入库、产品参数表治理
- **FR-003**: System MUST 按城市 / 线路 / 天气 / 车型做结构化过滤 + 自然语言语义召回；命中回跳视频时间戳；没标签 = 不存在
  - 来源：L2 L2-1 / L3 结构化过滤 + 文本检索双索引
  - 同族复用：素材库、工程影像库、案例库、投标文件库
- **FR-004**: System MUST 把 RoboBus 运营链拆成 城市/线路 → 车队与调度 → 乘客预约端 → 运营方结果 四环，每环绑定一个可量化运营指标 + 一个证据锚
  - 来源：L2 L2-2 / L3 运营场景价值主张结构化
  - 同族复用：任何 To G / To B 产品的"能力 → 运营结果"映射：云厂商、政务 SaaS、工业设备
- **FR-005**: System MUST 固定骨架 谁 · 在什么路况/时刻 · 遇到什么 · 车怎么应对 · 乘客或运营方得到什么 · 证据来自哪；骨架固定、表达可换
  - 来源：L2 L2-2 / L3 场景故事骨架
  - 同族复用：客户案例故事、展会解说稿、战报、对外版故障复盘
- **FR-006**: System MUST 同一事实核心，面向公交公司运营方 / 乘客 / 媒体 / 政府四种讲法不同；只换表达与例子，不换事实
  - 来源：L2 L2-2 / L3 受众分讲法改写
  - 同族复用：发布会多受众材料、投资者 / 客户 / 媒体三套说明
- **FR-007**: System MUST 每个可对外的数字与承诺有唯一 ID、当前版本、生效日期、停用标记；检索强制过滤"当前在售车型 + 当前生效版本"
  - 来源：L2 L2-3 / L3 对外口径卡（唯一权威事实表）
  - 同族复用：对外说明书、价目表、服务承诺口径、对外白皮书
- **FR-008**: System MUST 正文里的数字只允许来自 {{fact_id}} 占位符；校验器逐项比对口径卡，未替换占位符或不一致即阻断
  - 来源：L2 L2-3 / L3 正文占位符 + 发布前一致性校验
  - 同族复用：财报解读、投标文件、ESG 报告、对外白皮书
- **FR-009**: System MUST 禁用词表 + 规则正则 + LLM 语义判定（绝对化用语、未经证实的承诺、竞品比较边界）；拦截清单必须有人签字放行
  - 来源：L2 L2-3 / L3 合规红线双层校验 + 人工签字
  - 同族复用：广告合规、招聘 JD、外资披露材料、平台运营规范
- **FR-010**: System MUST 平台舆情工具 + 人工定时看两条路；发布前红线校验拦绝对化用语与越界竞品比较，发布后异常上升回溯当天发了什么；舆情不进内容生成链路，只做发布后的看和发布前的拦
  - 来源：L2 L2-3 / L3 舆情与调性管控
  - 同族复用：通用"对外内容合规"：法务审稿、政务发布、上市公司 IR 口径、平台社区运营
- **FR-011**: System MUST 发布时写入 选题ID / 场景标签 / 题材 / 时长 / 平台 / 发布时间；各平台数据手工或接口回填进同一张表
  - 来源：L2 L2-4 / L3 发布即绑定选题 ID + 效果回填
  - 同族复用：活动投放、电商详情页、SEO 内容、雇主品牌
- **FR-012**: System MUST 归因到可聚合的题材 / 场景 / 平台，而非单篇；存量内容回标建第一版"什么有效"基线
  - 来源：L2 L2-4 / L3 选题级归因 + 存量内容回标
  - 同族复用：内容复盘、投放素材效果回流、渠道组合分析
- **FR-013**: System MUST 审核台记录"采用 / 轻改 / 重写 / 弃用 + 原因"，回流成 few-shot 与风格约束；弃用理由是最贵的训练信号
  - 来源：L2 L2-4 / L3 采纳率回流校准
  - 同族复用：任何人机共写场景：客服话术、法务文书初稿、财报点评

## Success Criteria *(mandatory)*

### Measurable Outcomes

> 目标值来自题解的 OKR。**基线为 `Day1 实测` 的条目，在实测前不构成承诺。**
> 没有权威测评的指标一律标「我方验收目标（非业界实测）」。

- **SC-001**: 月有效线索数（可归因到选题与场景） → 目标 ≥ 基线 × 1.5（基线：Day1 实测（口径由市场部定义 ⚠️）；怎么量：发布时绑定选题 ID，后台回填线索；口径由市场部书面确认）　**北极星**
- **SC-002**: 单条内容生产周期（拿到选题→可发布初稿） → 目标 ≤ 3 小时（基线：Day1 实测（预估 1–3 天）；怎么量：流水线跑批计时，5 个选题取均值）
- **SC-003**: 素材复用率（新内容基于已有素材库的比例） → 目标 ≥ 60%（基线：当前极低；怎么量：内容引用素材 ID 计数）
- **SC-004**: 参数错误 / 合规违规的发布前拦截率 → 目标 = 100%（零违反）（基线：0（无机制）；怎么量：故意构造 10 条错误样本做对抗测试，拦截率必须 100%）
- **SC-005**: 存量内容标签化覆盖 → 目标 ≥ 200 条历史内容完成回标，产出首版选题洞察（基线：0；怎么量：标签库计数 + 洞察报告）
- **SC-006**: 市场部采纳率（AI 初稿被采用或轻改后发布） → 目标 ≥ 50%（基线：0；怎么量：审核台记录"采用 / 轻改 / 重写 / 弃用"）
- **SC-007**: 单条内容的人工审核与返工总时长 → 目标 不高于基线（基线：Day1 实测；怎么量：审核台计时（改稿轮次 × 耗时））　**护栏**
- **SC-008**: 舆情异常发现时延（异常上升 → 定位到当天发布的内容） → 目标 ≤ 2 小时（基线：当前靠人工刷，> 1 天；怎么量：舆情表每日拉数 + 异常告警；抽 10 次异常复盘计时）
- **SC-009**: 舆情与调性结论的人工确认率 → 目标 = 100%（基线：0；怎么量：舆情表每条结论带确认人；未确认不外发）

> 拆解计数核对：> L2-1 → 3 条，L2-2 → 3 条，L2-3 → 4 条，L2-4 → 3 条 = 13 条机制，不是 13 个 L2。L2 保持 4 条不变，这是深度控制。
