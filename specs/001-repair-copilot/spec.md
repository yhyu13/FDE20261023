### User Story 1 - 经验只存在于人脑，不存在于可检索系统 (Priority: P1)

**业务问题**：现场报修了，为什么还要从头查起？

**根因**：老师傅的排查顺序是口述的隐性知识；录成文字成本高，无人整理，离职即带走

**为什么值得做**：直接对应业务目标里的"工匠经验复用"；且是唯一不可从外部采购的资产

## Requirements *(mandatory)*

### Functional Requirements

> 每条 FR 来自一条 **L3 机制**，并注明它属于哪个 L2 缺口。
> 凡是**要签字的数字与参数**，FR 必须写明溯源要求；
> 凡是**低置信结果**，FR 必须写明人工确认要求。

- **FR-001**: System MUST 老师傅口述/现场随手记录 → ASR 转写 + LLM 代拟成标准条目（现象/可能原因/排查顺序/禁忌/所需备件）→ 老师傅只做"确认/改"，不做撰写
  - 来源：L2 L2-1 / L3 经验条目化工作台
  - 同族复用：任何"经验随人走"的场景：新产品工艺规程、老师傅质检判据、老中医经验方
- **FR-002**: System MUST 不是写成一段话，而是写成有序步骤树（分支条件 → 下一步），每步带观测点与判定标准
  - 来源：L2 L2-1 / L3 经验结构化为可执行排查路径
  - 同族复用：设备点检 SOP、巡检路线编排、应急预案决策树
- **FR-003**: System MUST 一条经验条目 = 一条带型号/规格与故障域上下文的排查路径；工单可反向引用它
  - 来源：L2 L2-1 / L3 经验与工单双向绑定
  - 同族复用：质量事故案例库、新员工带徒教材、审计举证
- **FR-004**: System MUST 用业务语言定义 RepairObject / Fault / AlarmCode(FaultCode) / RepairAction / Part / Technician / WorkOrder / ManualSection，并提前固化关联（型号/规格↔手册版本↔章节、现象↔码↔部件、订单↔备件↔技师）
  - 来源：L2 L2-2 / L3 工单本体（Ontology）
  - 同族复用：通用"制造/服务/巡检"对象模型；换行业只换实体名
- **FR-005**: System MUST 料号、报警码/故障码、手册章节号、型号/规格配置各给唯一 ID 与版本；变更有生效日期
  - 来源：L2 L2-2 / L3 主数据统一编码
  - 同族复用：备件主数据、设备台账、固定资产编码统一
- **FR-006**: System MUST 任何检索与建议都必须带型号/规格/配置过滤；无匹配则明确说"无手册依据"，不猜
  - 来源：L2 L2-2 / L3 型号/规格约束强制校验
  - 同族复用：多规格多配置产品的选型与报价防错
- **FR-007**: System MUST 人工维护主干（码 → 标准现象描述），从历史工单反向挖掘补充同义映射；技师输入先做症状归一化再进检索
  - 来源：L2 L2-3 / L3 现象 ↔ 报警码/故障码映射表
  - 同族复用：客服工单分类、售后问诊分流、设备报警代码归一
- **FR-008**: System MUST 结构化过滤（型号/规格/码域）+ 语义召回（手册语言）+ 关键词召回（料号/码）三路并集后重排
  - 来源：L2 L2-3 / L3 检索双过滤 + 混合召回
  - 同族复用：法规/标准/合同条款检索
- **FR-009**: System MUST 从历史工单反推每名技师的"擅长故障域 × 熟悉型号/规格 × 认证资质 × 通过率"
  - 来源：L2 L2-4 / L3 技师技能画像
  - 同族复用：岗位胜任力画像、招聘匹配、外包队伍能力评估
- **FR-010**: System MUST 得分 = 技能匹配 + 故障域重合 + 班次可用 + 资质合规，输出 Top-N 与选他/不选他的理由
  - 来源：L2 L2-4 / L3 派工匹配打分 + 理由生成
  - 同族复用：抢单派单、值班排班、维修工程师分派
- **FR-011**: System MUST 技师勾选执行的步骤与最终原因回写工单；每条闭环工单自动成为评测样本；误判案例回流为 few-shot 与规则修正
  - 来源：横贯 / L3 回写闭环 + 闭环即评测
  - 同族复用：所有"人在回路"的 AI 系统通用：合同审核、质检判定、客服工单

## Success Criteria *(mandatory)*

### Measurable Outcomes

> 目标值来自题解的 OKR。**基线为 `Day1 实测` 的条目，在实测前不构成承诺。**
> 没有权威测评的指标一律标「我方验收目标（非业界实测）」。

- **SC-001**: 同型号/规格同故障的首次诊断命中率（历史回测 Top-1） → 目标 ≥ 70%（基线：Day1 实测；怎么量：历史已闭环工单回测脚本，随代码入库）　**北极星**
- **SC-002**: 技师获取排障信息耗时 → 目标 ≤ 2 分钟（基线：Day1 实测（预估 20 分钟+）；怎么量：5 名技师各测 3 次现场计时）
- **SC-003**: 派工建议采纳率 → 目标 ≥ 60%（基线：0；怎么量：班长确认采用数 / 总建议数（一周内））
- **SC-004**: 老师傅经验条目化且被检索命中 → 目标 ≥ 200 条（基线：0；怎么量：知识库计数 + 命中率日志）
- **SC-005**: 建议准确率（人工抽检） → 目标 ≥ 80%（基线：—；怎么量：抽 50 条，技师判"可直接执行/需修改/不可用"）
- **SC-006**: 经验条目由老师傅本人确认的比例 → 目标 ≥ 60%（基线：0；怎么量：条目确认人字段统计（护栏：防止 AI 自说自话））
- **SC-007**: 二次上门率 → 目标 不高于基线（基线：Day1 实测；怎么量：报修工单闭环数据回看）　**护栏**

> 拆解计数核对：> L2-1 → 3 条，L2-2 → 3 条，L2-3 → 2 条，L2-4 → 2 条，横贯 → 1 条。L3 是 11 条机制，不是 11 个 L2。 L2 保持 4 条不变，这是深度控制。
