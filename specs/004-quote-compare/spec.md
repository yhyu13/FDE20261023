### User Story 1 - 报价单与基准清单之间没有统一的行结构 (Priority: P1)

**业务问题**：报价各说各话，工程分包怎么比？

**根因**：每家表结构、品名写法、计量颗粒度都不同（有的把桩基检测按桩计、有的按米计；有的合并报、有的拆细报）

**为什么值得做**：没有共同坐标系，"谁便宜"这个问题根本无法被形式化；这是所有后续动作的前提

**Independent Test**: ⚠️ 待补——写清「怎么单独验收这一条」，以及「只实现这一条时交付什么」。

**Acceptance Scenarios**: ⚠️ 待补——Day1 现场按真实业务动作补 Given/When/Then。

### User Story 2 - 各家的"总价"不是同一件事（口径不可比） (Priority: P2)

**业务问题**：报价各说各话，工程分包怎么比？

**根因**：含税/不含税、含不含运费、含不含甲供材、措施费、暂列金、暂估价、计价依据版本（GB/T 50500-2024 还是旧版）各报各的

**为什么值得做**：口径不统一时任何排序都是错的——这是本题真正的深水区，也是"归集比对"四个字的难点所在

### User Story 3 - 漏项与多项不可见 (Priority: P3)

**业务问题**：报价各说各话，工程分包怎么比？

**根因**：少报的项目是后期变更与索赔的来源；多报、拆分合并导致错配与重复计价

**为什么值得做**：直接对应业务目标里的"归集比对"；也是评审与审计最关心的一栏

### User Story 4 - 台账数字不可溯源、评审过程不留痕 (Priority: P4)

## Requirements *(mandatory)*

### Functional Requirements

> 每条 FR 来自一条 **L3 机制**，并注明它属于哪个 L2 缺口。
> 凡是**要签字的数字与参数**，FR 必须写明溯源要求；
> 凡是**低置信结果**，FR 必须写明人工确认要求。

- **FR-001**: System MUST Objects（Quote / QuoteLine / BillItem / Bidder / Offer / 口径标记）→ Links（QuoteLine ↔ BillItem 基准映射、QuoteLine ↔ 源定位）→ Actions+Write-back（确认即定稿、改动留痕）
  - 来源：L2 L2-1 / L3 报价行本体（Ontology 三步法）
  - 同族复用：通用"多主体方案横向比"对象模型；换行业只换实体名（供应商/投标/比选同构）
- **FR-002**: System MUST Excel 取计算值不取公式串；扫描件走 OCR + 表格结构还原；每行携带源定位与置信度
  - 来源：L2 L2-1 / L3 多格式解析管线（xlsx / PDF 文本层 / PDF 扫描件分层）
  - 同族复用：合同、投标文件、检测报告、结算单的多格式归集通用
- **FR-003**: System MUST 历史别名表优先；无别名时给候选（规格 + 单位 + 语义相似）；禁止模型静默归一，一律人工选
  - 来源：L2 L2-1 / L3 品名别名与规格映射表
  - 同族复用：物料主数据归并、产品线对标、跨系统科目映射
- **FR-004**: System MUST 规则表由商务给并签字，每条写死：含税与否、税率、运费、甲供材、措施费、暂列金、计价依据版本；归一计算在确定性代码里跑
  - 来源：L2 L2-2 / L3 口径标记与归一引擎（规则表驱动）
  - 同族复用：规则表与行业无关，可复用到分包、采购、外协、设备租赁
- **FR-005**: System MUST 每份报价记录其报价依据（GB/T 50500-2024 等）与版本生效区间；版本不一致 → 标"口径存疑"，不自动归一
  - 来源：L2 L2-2 / L3 计价依据版本作为显式字段
  - 同族复用：任何"按不同版本标准/规范报价"的场景：软件版本、检测规程、设计规范
- **FR-006**: System MUST 原始价 / 归一价 / 可比单价并排；总额不可比；未定义口径的行标"不可比"并单列，不参与排序
  - 来源：L2 L2-2 / L3 可比单价与三视图
  - 同族复用：任何"总价不可比、要按单位能力比"的场景：物流单价、服务人天、材料单价
- **FR-007**: System MUST 与我方清单（锚定 GB/T 50500-2024）双向比对：缺项、名称不匹配、数量偏差超阈值、同一项被拆成多行
  - 来源：L2 L2-3 / L3 基准清单双向 diff
  - 同族复用：通用"应有 vs 实有"校验器：报价 vs 清单、发货 vs 订单、清单 vs 结算
- **FR-008**: System MUST 单价离群、合价不平衡、分项和≠合计、税率异常、同一项在不同家数量不一致
  - 来源：L2 L2-3 / L3 异常检测（离群 / 逻辑冲突 / 算术平衡）
  - 同族复用：通用"低频错误抓取"：体检指标异常、结算单不平、发票重复
- **FR-009**: System MUST 每个数字记录 源文件 → 页码/单元格 → 原文片段 → 解析置信度；台账上可点开看原图/原表
  - 来源：L2 L2-4 / L3 数字级溯源（源定位）
  - 同族复用：审计、举证、复核通用件（检测数据、验收记录、结算单同构）
- **FR-010**: System MUST 原始件哈希、每次修改记 who/when/what、原表只读快照、评审意见归档、导出带溯源脚注
  - 来源：L2 L2-4 / L3 审计留痕与原表只读快照
  - 同族复用：合同评审、采购评审、内控检查通用
- **FR-011**: System MUST Decimal 定点；求和、乘除、税率换算、可比单价、平衡校验全部在代码里；单元测试覆盖，等于 0
  - 来源：横贯 / L3 确定性算术内核
  - 同族复用：任何"数字要签字"的场景通用：结算、对账、计量、绩效核算
- **FR-012**: System MUST 无映射 / 口径存疑 / 算术不平 / 版本不一致 → 进确认队列；未确认不得进主表
  - 来源：横贯 / L3 低置信度人工确认台
  - 同族复用：任何"自动结果可能出错且要签字"的场景通用

## Success Criteria *(mandatory)*

### Measurable Outcomes

> 目标值来自题解的 OKR。**基线为 `Day1 实测` 的条目，在实测前不构成承诺。**
> 没有权威测评的指标一律标「我方验收目标（非业界实测）」。

- **SC-001**: 比选台账产出耗时（归集 + 比对 + 生成，含人工确认环节） → 目标 ≤ 1 人 × 2 小时（基线：Day1 实测（预估 2 人 × 1 天）；怎么量：端到端计时，含确认环节）　**北极星**
- **SC-002**: 报价行归一准确率（数量 / 单价 / 金额三项都对） → 目标 ≥ 95%（抽 100 行人工核对）（基线：—；怎么量：人工抽检表）
- **SC-003**: 漏项 / 口径异常检出率 → 目标 ≥ 90%（用历史 3 次比选回测，真漏项能抓到）（基线：—；怎么量：回测脚本，随代码入库）
- **SC-004**: 数字可溯源率 → 目标 100%（台账每个数字能点回原文件位置）（基线：0；怎么量：抽样 50 个数字逐一点开）
- **SC-005**: 台账一次签字通过率 → 目标 ≥ 70%（商务负责人未要求修改数字的比例）（基线：—；怎么量：评审记录）
- **SC-006**: 口径规则覆盖率 → 目标 我方确定口径（含计价依据版本）100% 有明确规则，无"未定义口径"行（基线：0；怎么量：规则表 vs 实际数据交叉检查）
- **SC-007**: 未经确定性校验或未经人工确认即进入台账主表的行数 → 目标 = 0（基线：0；怎么量：审计日志 + 对台账全量复跑校验脚本，违规 0 行）　**护栏**
