# FDE 训练营 · 仓库宪法（Constitution）

> **这份文件是 spec-kit 的 `constitution.md`，但它不是新规矩。**
> 它把 [`AGENTS.md`](../AGENTS.md) 翻译成 spec-kit 在**每个阶段自动检查**的那几条——
> 如果这里写的是模板占位符，检查就形同虚设。
>
> **冲突时以 `AGENTS.md` 为准。** 本文件是索引 + 一条 spec-kit 独有的。

---

## 核心原则

### 一 · 拆解只到三层，且不得变形

> 对应 `AGENTS.md` §2。

**L1 业务问题 → L2 能力缺口 → L3 可复用机制，就三层。**

- L2 必须是**能力缺口**，不是症状（"查手册慢"是症状，"手册与工单没有可检索的结构化关联"才是缺口）
- L3 必须是**可复用的做法**，不是功能名（"做一个派工功能"是功能名，"技师技能画像 + 约束匹配打分"是机制）
- **不允许出现第 4 层**：L3 内部的步骤属于"实现要点"，写进说明列或专项技术点章节

在 spec 层面：一条 **FR / 用户故事只能落在一个 L2 上**，落不上的说明还没拆透。

### 二 · 先见红，再写实现（TDD，不可协商）

> 对应 `AGENTS.md` §5、§6。

```
红    写一条最小测试，只测一件事，名字说清行为
  ↓  跑它，确认【失败】，且失败原因正是「功能还没实现」
     ——如果是因为打错字或测试本身报错，先修到「以正确的原因失败」
绿    写最少的代码让它过。不顺手重构、不加需求外的东西
  ↓  跑它，确认通过，且其它测试也都还绿
重构  只在绿的时候做。保持绿，不改变行为
```

**"确认红"这一步最容易被跳过、也最不能跳。** 它是整个流程唯一能告诉你
"你的测试有没有在测东西"的动作。**没有亲眼看着那个测试失败过，就不知道它在测什么。**

### 三 · 事实必须可溯源，模型不做算术

> 对应 `AGENTS.md` §3、§4。

- 凡是**要签字的数字与参数**（报价、比选台账、溯源报告、对外口径），
  必须能回链到**原始文件的具体位置**，否则不成立。
- **LLM 不做算术**。求和、乘除、比值、税率换算一律走确定性代码。
- **LLM 不编事实**。低置信度的抽取结果必须走**人工确认台**，
  没确认的不许进主表、不许发布、不许作为证据。
- 企业侧未提供、且公开渠道也查不到的信息，标 `⚠️ 待现场确认`——**不臆造**。

### 四 · 一 spec 一交付，AC 与测试同名

> 对应 `AGENTS.md` §7、§8。

- 一次 spec 只覆盖**一个可独立交付**的范围。太大就拆，用依赖串起来。
- **每条 AC 必须有一条同名测试**（名字以 AC 编号开头）。对不上号的两边都要改，不许留悬空的。
- spec 的 **Success Criteria 必须可测**，不是"体验流畅"、"更智能"。
  目标值写清楚是"**我方验收目标**"还是"**业界实测**"——后者没有权威来源就不许写。

### 五 · 举一反三：机制必须可复用，不是宏大空话

> 对应 `AGENTS.md` §9。

每个 L3 机制必须标出**它还能一并解决什么**。同族问题判定三条同时成立才算：

1. **同一类数据形态**
2. **同一类痛点**
3. **不需要换业务知识就能复用**

**反面例子（禁止）**："这个方案还能用于教育行业"——数据形态和痛点都变了，只是听起来宏大。

## 附加约束

### 技术栈

| 域 | 规定 | 理由 |
|----|------|------|
| 语言 | **Python 3.11+**（本机 3.13） | 六道题都要处理非结构化输入 + 检索/求解，生态在这 |
| 依赖管理 | **uv**（`uv sync` / `uv run`），不裸 pip | `uv` 已在 PATH；锁文件入库 |
| 框架 | 内部 demo 用 **Streamlit / Gradio + pandas**；需要被调用的才上 **FastAPI + uvicorn** | FDE 方法论：先跑通再谈工程化 |
| 存储 | **SQLite**（原型期）；Postgres 只在明确需要并发写时引入 | 客户环境可能断网，见 §数据安全 |
| 部署 | **Docker Compose**，离线可跑 | 客户内网常无外网 |
| Lint / 测试 | **ruff** + **pytest**，`uv run` 统一入口 | 闸要能机械执行 |

### 数据安全（硬红线）

- 客户数据**不出厂区**：默认内网/离线部署，模型调用走客户许可的通道。
- 商业报价、个人身份信息属敏感数据：**不进日志、不进 prompt、不入库到第三方服务**。
- 演示用数据必须是**脱敏样本或合成数据**。真实数据只在客户现场、当场、经授权使用。

### 数值与准确率

- **没有权威测评，就不给准确率数字。** KR 里的目标值必须标注"我方验收目标（非业界实测）"。
- 基线未知的，标 `Day1 实测`——不许先填一个好看的数。

## 开发工作流

### 五步 SDD（spec-kit）

```
/speckit.constitution  →  宪法（= 本文件，一次性，后续少动）
/speckit.specify       →  specs/NNN-slug/spec.md      用户故事 + FR + AC + SC
/speckit.plan          →  specs/NNN-slug/plan.md      技术方案 + 数据模型 + 契约
/speckit.tasks         →  specs/NNN-slug/tasks.md     可执行任务（带依赖，可并行）
/speckit.implement     →  按 tasks.md 执行，每个任务走 TDD 红→绿→重构
```

辅助命令：`/speckit.clarify`（消歧）、`/speckit.analyze`（跨产物一致性检查）、
`/speckit.checklist`（需求完备性清单）、`/speckit.taskstoissues`（任务转 issue）、
`/speckit.converge`（回扫代码库补任务）。

**六道真题的 spec 不是从零写**：`problems/*.md` 的三层拆解树已经是 80% 的 spec，
用 `tools/seed_spec.ps1` 一键灌进 spec-kit 的结构里。

### 闸（机械拦截，不靠记性）

`tools/run_all_gates.py` 统一跑，**看 `$LASTEXITCODE` / 退出码，不看输出文本**。
状态有三种：**OK / FAIL / SKIP**。

> **SKIP 不是 OK。** 没有测试就记 SKIP，并在结论行写明"这不等于全部通过"。
> 把"没跑"写成"通过了"是本项目最贵的病。

### 变更流转

- 分支：`feat/NNN-slug` 或 `fix/<短名>`；**一 feature 一分支**。
- **一 worktree 一会话**：同一棵工作树，同一时间只允许一个会话在写。
- 改动走 **PR**；PR 必须带：动了哪条 AC、测试证据、闸结果、**没做什么**。
- **只 `git add <明确列出的文件>`，绝不 `git add -A`**——隔壁 worktree 的
  诊断脚本、一次性探针随时可能躺在旁边，`-A` 会把它们卷进你的提交。

### 必须停下来问，不许自己决定

0. 打 tag / 发版本 / 推 tag
1. 任何**部署到公网**的动作
2. 删除用户数据或远端分支
3. 改动**验收标准本身**（新增/删除 AC、动 spec 的验收口径）
4. 绕过闸（`--no-verify` / `git commit -f`）——允许，但**必须在提交信息里写清为什么**
5. 发现另一个会话在同一棵工作树里活动
6. 合并到 `main` 以外的任何共享分支

## 治理

- 本宪法**优先于其它一切实践**。与 `AGENTS.md` 冲突时以 `AGENTS.md` 为准；
  与任何一次性计划冲突时以本文件为准。
- **修订宪法需要**：写清改动原因 + 影响面 + 迁移方式，并走 PR。
- 每次 PR 的评审**必须核对**本宪法的五条原则。
- 复杂度必须被论证："为什么这个方案不是三行代码"要有答案。
