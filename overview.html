现场拿到的不是练习题，是四家企业挂在生产上的真问题：客车维修为什么每次都从头查起、蓝莓的每一步能不能有据可查、 分包报价各说各话怎么比、上百张现场照片隐患藏在哪、上千名护士培训该派谁。 每一题都拆成同一套五段：场景 → 项目 → 专项技术点 → OKR → 解决方案， 并且只用一个北极星业务指标衡量成败——不是功能数量。

申沃客车

上海申沃客车有限公司 · 上汽集团全资客车研发制造企业

2000 年成立，闵行莘庄工业区；车型 7–27 米，覆盖纯电 / 燃料电池 / 插混；累计销售 4.3 万台大中型客车；9 系配 ADAS 智能驾驶辅助系统。2026-06 与享道出行（SAIC 移动出行品牌）签「数字化+智能化」战略合作：车联网平台、RoboBus 自动驾驶、AI 大模型，享道输出 Robotaxi 云控架构并联合构建车辆监控调度平台与乘客预约客户端，明确「推动 AI 融入研发、生产、售后全流程」。

校准：真空白不是「没有系统」——售后已用简道云零代码做过试点，同业宇通已有智能远程诊断。缺的是经验没结构化 + 派工没数据化。且它的售后是车队型运营商的售后，目标函数是恢复运营，不是修好。题 02 在业务上等于「从卖车转向卖运营服务」。

蓝莓研究所

上海市蓝莓研究所 · 民办非企业单位 · 主管：上海市绿化和市容管理局

2012-01-18 成立，上海金山区吕巷镇，所长陆敏。牵头起草上海市地方标准《蓝莓栽培技术规范》（2023-10 通过技术审查）；敏蓝「五个统一」质量管理体系获第九届金山区区长质量奖；基地有物联网智慧农业肥水一体化自动灌溉；中央财政项目辐射带动 502 亩；田间学校培训 6000 余人次。

校准：不是种植企业，是技术推广方——资产是「标准 + 品种 + 技术 + 培训」，服务半径远超自有基地。真问题不是「给自己建档」，而是「把标准、种苗、技术指导的交付过程沉淀成可复核的数据」。
同族参照：麻江县已有产业级蓝莓大数据平台（117 类种质、近 10 年数据），官方承认的缺口是数据「大多停留在农户脑海，没有形成标准化、结构化的数据」。

六题共用的骨架

拆解语言不临时发明，全部沿用既有 FDE 方法论——这决定了六份方案能在同一支团队手里并行推进。

Ontology 三步法

用业务语言定义对象（车、批次、地块、护士），提前固化关联，动作能反写回系统。不让模型直接啃原始表。

Echo + Delta

Echo 负责听懂业务并定义问题，Delta 负责快速交付可跑结果。缺 Echo 变咨询，缺 Delta 变外包。题 02 是 Echo 主导的题。

5 天一个 demo 节点

不写长需求文档，每 5 天一次客户可见演示。本仓按训练营的 3 天节奏给到 Day1–Day3 交付物。

碎石路 → 高速公路

题 01 / 申沃客车 · 智能制造

现场报修了，为什么还要从头查起？

业务目标：现场维修智能协同、派工建议与工匠经验复用 · 2 组 · Echo 售后技术主管/老师傅 · Delta 算法+后端

工单 Ontology混合检索 RAG故障树推理 技能画像派工Write-back离线回测内网部署

三层拆解树 · L1 → L2 → L3

L1

现场报修了，为什么还要从头查起？

  • L2-1经验只存在于人脑，不存在于可检索系统

    根因：老师傅的排查顺序是口述的隐性知识，录成文字成本高、无人整理、离职即带走。

    • 经验条目化工作台：口述/随手记录 → AI 代拟成标准条目 → 老师傅只做确认 同族复用 · 新产品工艺规程 · 质检判据 · 经验方
    • 经验结构化为可执行排查路径：有序步骤树（分支条件→下一步），每步带观测点与判定标准 同族复用 · 设备点检 SOP · 巡检路线 · 应急决策树
    • 经验与工单双向绑定：一条经验 = 一条带车型/故障域上下文的排查路径 同族复用 · 事故案例库 · 带徒教材 · 审计举证
  • L2-2工单 / 故障码 / 手册 / 车型四种载体彼此不连通

    根因：现象、码、部件、车型、章节各自成表，查询时临时拼接。车型 7–26m × 多动力形式，跨车型串检是真实事故风险。

    • 工单本体（Ontology）：Vehicle·Fault·Code·Action·Part·Technician·Order，Links 提前固化 同族复用 · 制造/服务/巡检通用对象模型
    • 主数据统一编码：料号/码/章节号/车型配置唯一 ID + 版本 + 生效日期 同族复用 · 备件主数据 · 设备台账 · 资产编码
    • 车型约束强制校验：无匹配就明说"无手册依据"，不猜 同族复用 · 多规格多配置选型与报价防错
  • L2-3现场输入的口径与知识库口径对不上

    根因：技师说"起步发闷"，码表写 P0AA6，手册写"驱动系统功率限制"——检索第一道门就漏。

    • 现象 ↔ 故障码映射表：主干人工维护 + 从历史工单挖掘同义映射，输入先做症状归一化 同族复用 · 工单分类 · 问诊分流 · 报警码归一
    • 检索双过滤 + 混合召回：结构化过滤 + 语义召回 + 关键词召回三路并集后重排 同族复用 · 法规/标准/合同条款检索
  • L2-4派工与技师能力没有数据化

    根因：靠班长对"谁熟哪款车、哪类故障"的记忆。

    • 技师技能画像：从历史工单反推「擅长故障域 × 熟悉车型 × 认证资质 × 通过率」 同族复用 · 岗位胜任力画像 · 招聘匹配 · 外包队伍评估
    • 派工匹配打分 + 理由生成：得分可解释，输出"选他 / 为什么不选他" 同族复用 · 抢单派单 · 值班排班 · 工程师分派

L2 = 4 条能力缺口 · L3 = 11 条机制（3+3+2+2+横贯 1）· 另有一条横贯缺口「结果不回流成可复用知识」→ 机制：回写闭环 + 闭环即评测

场景：经验在脑子里，历史工单检索不了

技师到场处置要经过「确认车型 → 判断原因 → 逐条排查 → 备件 → 复检关单」。中间两步是黑洞：判断依据是老师傅口口相传，历史工单只写了自由文本，检索等于没有。

  • 查手册慢：PDF 无结构，靠翻章节
  • 历史工单用不上：没有统一故障码/部件/步骤字段
  • 经验留不下：录成文字成本太高，无人整理
  • 派工靠拍脑袋：技师擅长什么没有数据化

项目：维修协同助手 Repair Copilot

输入
车架号/车型 + 故障现象（文字/照片/故障码）
输出
候选故障原因 Top-N · 推荐排查步骤 · 携带配件清单 · 建议派工
溯源
每条结论指回手册章节 / 历史工单 / 经验条目
砍掉
不改工单系统本体 · 不接实时库存 · 不做自动报价
范围
只覆盖 Top 20 高频故障码/现象

解决方案：从原始工单到可回写的答案

OKR

O：让现场维修从「凭经验从头查起」变成「带着答案进场」，让老师傅的经验第一次成为可复用资产。

首次诊断命中率（北极星）
≥70%
建议准确率
≥80%
派工建议采纳率
≥60%
获取排障信息耗时
≤2min
老师傅经验条目化
≥200条

护栏：二次上门率不得高于基线。工具让技师"照系统走"而漏掉真原因，即使命中率达标也算失败。

三天节奏

  1. Day1 · 开题

    2 小时老师傅访谈 + 100 条脱敏工单 + 手册 + DTC 表；定 Top20 故障范围。

  2. Day2 · 共解

    抽取归一管线、手册索引、检索+故障树服务、工单侧边栏；离线回测跑第一版基线。

  3. Day3 · 出厂

    用真实故障码端到端走一遍；老师傅逐条打分；打通回写。

最大风险：老师傅不愿配合或没时间 → 兜底是「语音录入 + AI 代拟，他只做确认」，同时把范围砍到 Top20 故障码。
题 02 / 申沃客车 · 品牌传播

申沃的智能驾驶，下一站开向哪里？

业务目标：智能驾驶品牌营销、场景化传播与内容持续运营 · 2 组 · Echo 主导 市场部/品牌负责人 · Delta 内容流水线工程师

多模态打标品牌知识库 RAG内容 Agent 流水线 参数与合规校验选题级归因审核台Echo 主导题

三层拆解树 · L1 → L2 → L3

L1

申沃的智能驾驶，下一站开向哪里？

  • L2-1素材与运营数据没有变成可检索的场景事实

    根因：售后侧已有零代码试点，但市场侧素材仍只是视频、里程、接管事件这些非结构化资产，只以文件名与口述存在。

    • 多模态素材场景打标管线：抽帧 → VLM 生成描述 → 归一为受控标签 + 人工纠正回写 同族复用 · 展会录像 · 现场施工照片 · 培训录像 · 开箱视频
    • 事实原子抽取与归一：抽成「主体 + 指标 + 数值 + 口径 + 时点 + 出处」，同名指标只留一条，分歧显式标出 同族复用 · 财报数据抽取 · 招投标参数归集 · 质检指标入库
    • 结构化过滤 + 文本检索双索引：没标签 = 不存在 同族复用 · 素材库 · 工程影像库 · 案例库
  • L2-2讲得出参数，讲不出运营价值

    根因：内容停在"自动驾驶 / 激光雷达 / 算力"的概念与技术层，RoboBus 的价值在运营链路（城市线路、车队调度、乘客预约、运营方结果），这条链路没被翻译成内容语言。

    • 运营场景价值主张结构化：城市/线路 → 车队与调度 → 乘客预约端 → 运营方结果，每环绑一个可量化指标 + 一个证据锚 同族复用 · 任何 To G / To B 的「能力→运营结果」映射
    • 场景故事骨架：谁 · 什么路况时刻 · 遇到什么 · 怎么应对 · 得到什么 · 证据来自哪（骨架固定、表达可换） 同族复用 · 客户案例 · 展会解说稿 · 战报
    • 受众分讲法改写：运营方 / 乘客 / 媒体 / 政府四种讲法，只换表达不换事实 同族复用 · 发布会多受众材料 · 投资者/客户/媒体三套说明
  • L2-3对外事实没有唯一版本与出处，发布前拦不住

    • 新人判据卡（把老手的"看"变成可交接的规则）：每条判定条目配：① 判据（一句话，说清"什么算隐患"）；② 看图要点（该看画面哪个位置）；③ 依据出处（条目号 + 原文）；④ 1–2 张正例/反例图。新人按卡片自查，老手按卡片复核 同族复用 · 通用"隐性经验显性化"：老师傅工艺判据、老中医经验方、质检眼力、带徒教材
    • 风险分级映射表 + 评测集（分条目出指标）：隐患类别 → 风险等级 → 整改要求，分级口径来自甲方既有制度，不由模型定级；用甲方真实照片人工标注建集，按条目分别出召回 / 精确率与混淆样本图 同族复用 · 所有"小样本视觉任务"的通用评测范式
  • L2-4风险源与不符合项没有对象链，归档与整改闭环是断的

    根因：业务目标"归档 + 不符合项速查"

    • 不符合项对象链与闭环台账：Photo → DetectedHazard → Nonconformity → Rectification → RecheckPhoto；每步带责任人、期限、状态 同族复用 · 质量 / 安全 / 合规类问题闭环通用
    • 前后对照视图 + 归档台账导出：同一不符合项的隐患照与复查照并排（部位 / 时间 / 说明）；导出安全台账与归档索引（编号、类别、等级、责任人、期限、状态、照片索引） 同族复用 · 复查比对、索赔取证、创优工程资料归档通用
    • 外业数据备份与介质防护提醒：归档链自带"原始件只读副本 + 校验哈希 + 异地/云备份位"，导出时提示"硬盘未做防震/防水/防尘"这条行业风险 同族复用 · 通用"原始数据保全"：测绘原始数据、试验原始数据、影像原始文件
  • 横贯 人工复核队列 + 否认样本回流

    跨 L2 的横贯机制

    • 人工复核队列 + 否认样本回流：置信度分档；确认 / 否认；否认样本回流成 few-shot 与评测集；不自动开整改通知 同族复用 · 任何 CV 落地都要用的置信度管理范式
  • 横贯 引用白名单与范围声明

    跨 L2 的横贯机制

    • 引用白名单与范围声明：模型只能引用甲方检查表与适用判定条目；不得引用公开通用经验库或公开数据集冒充现场依据；对外输出必须写明所依据的条目号 同族复用 · 审计与合规场景的通用"来源可追"约束

三层拆解树 · L1 → L2 → L3

L1

上千名护士，这次培训到底该安排谁？

  • L2-1"谁该训"没有可执行、且可分层的判定口径

    根因：规则来自三类互不相同的权威来源——人社局职业技能等级认定目录（证书种类与有效期）、卫健口径、《新入职护士培训大纲（试行）》（主要适用三级综合医院）；而服务的医院口径不统一（三级综合 / 二级 / 民营），同一套清单不能直接套全部机构；这些规则还散在制度文件与口述里，各院 Excel 各写各的

  • L2-2硬约束只存在于人的判断里，机器给不出零违反保证

    根因：证书有效期、先修、岗位职称匹配、班次冲突、名额、医院配额、排班滞后，全部靠翻表和记忆；改一轮名单崩一轮

  • L2-3名单不可解释、不可干预

    根因：选派说不出"为什么是他"，未入选说不出"为什么不是他"；医院一句"换人"就得从头重排

  • L2-4跨月资源冲突与分层公平不在同一个模型里

    根因：只看单月，讲师 / 场地 / 时段冲突月底爆发；同一批人反复被排；三级综合与民营医院的公平与容量口径也不同

  • L2-5名单没有正式依据的版本与留痕，执行效果也不回流

    根因：名单是给医院与卫健看的正式依据，现在只是一份 Excel；谁在何时基于哪版规则改的、依据是什么事后说不清；排了没来的数据也回不来

L2-1 → 3 条，L2-2 → 3 条，L2-3 → 2 条，L2-4 → 2 条，L2-5 → 2 条 = 12 条机制，不是 12 个 L2。L2 保持 5 条不变（这是深度控制的上限，不再加）。

场景：改三轮还排不平

证书有效期、先修课程、岗位职称匹配、名额、班次冲突、医院配额——约束多到人脑记不住。Excel 拉名单 → 人工避冲突 → 排不满再手调 → 医院要换人 → 再改，改三轮还常漏人。

  • 漏人：靠人记，"该训"没训全
  • 排不满/排错班：约束没写出来
  • 医院要换人：名单不可解释，双方没有依据
  • 跨月排不开：只看单月，月底资源冲突爆发

05

结项要交什么

训练营官方口径：实战收获 = 真实卡顿 · 团队 AI 模型 · 测试与验证记录。结项交的是可验证的 AI 原型，不是 PPT。

真实卡顿

每题记录 2 次实际踩坑：数据格式、接口、口径、模型失败样本。这是训练营明确要求的第一项产出。

团队 AI 模型

不是"我们用了大模型"，而是带评测集的模型：回测脚本 + 评测集入库，跑得出分数。

测试与验证记录

甲方人工抽检表、断言报告、干预演示记录——每条建议"可用/需改/不可用"由甲方签字。

可复用件

每题标出哪些沉淀成通用件。碎石路修成高速公路，是 FDE 模式能规模化的前提。

三条贯穿六题的硬规矩：① 模型不做算术、不编事实，凡是要签字的数字与参数都必须可溯源； ② 低置信度结果必须走人工确认台，自动化率再高也不取消这一步； ③ 每题都有护栏指标（不恶化 / 零违反 / 不超基线），只报好看的那条不算达标。
