上海申沃客车有限公司 · 上汽集团全资客车研发制造企业

2000 年成立，闵行莘庄工业区；车型 7–27 米，覆盖纯电 / 燃料电池 / 插混；累计销售 4.3 万台大中型客车；9 系配 ADAS 智能驾驶辅助系统。2026-06 与享道出行（SAIC 移动出行品牌）签「数字化+智能化」战略合作：车联网平台、RoboBus 自动驾驶、AI 大模型，享道输出 Robotaxi 云控架构并联合构建车辆监控调度平台与乘客预约客户端，明确「推动 AI 融入研发、生产、售后全流程」。

六题共用的骨架

拆解语言不临时发明，全部沿用既有 FDE 方法论——这决定了六份方案能在同一支团队手里并行推进。

Ontology 三步法

用业务语言定义对象（车、批次、地块、护士），提前固化关联，动作能反写回系统。不让模型直接啃原始表。

Echo + Delta

Echo 负责听懂业务并定义问题，Delta 负责快速交付可跑结果。缺 Echo 变咨询，缺 Delta 变外包。题 02 是 Echo 主导的题。

5 天一个 demo 节点

不写长需求文档，每 5 天一次客户可见演示。本仓按训练营的 3 天节奏给到 Day1–Day3 交付物。

题 01 / 申沃客车 · 智能制造

现场报修了，为什么还要从头查起？

业务目标：现场维修智能协同、派工建议与工匠经验复用 · 2 组 · Echo 售后技术主管/老师傅 · Delta 算法+后端

工单 Ontology混合检索 RAG故障树推理 技能画像派工Write-back离线回测内网部署

三层拆解树 · L1 → L2 → L3

L1

现场报修了，为什么还要从头查起？

  • L2-1经验只存在于人脑，不存在于可检索系统

    根因：老师傅的排查顺序是口述的隐性知识；录成文字成本高，无人整理，离职即带走

    • 经验条目化工作台：老师傅口述/现场随手记录 → ASR 转写 + LLM 代拟成标准条目（现象/可能原因/排查顺序/禁忌/所需备件）→ 老师傅只做"确认/改"，不做撰写 同族复用 · 任何"经验随人走"的场景：新产品工艺规程、老师傅质检判据、老中医经验方
    • 经验结构化为可执行排查路径：不是写成一段话，而是写成有序步骤树（分支条件 → 下一步），每步带观测点与判定标准 同族复用 · 设备点检 SOP、巡检路线编排、应急预案决策树
    • 经验与工单双向绑定：一条经验条目 = 一条带型号/规格与故障域上下文的排查路径；工单可反向引用它 同族复用 · 质量事故案例库、新员工带徒教材、审计举证
  • L2-2工单 / 报警码（故障码）/ 手册 / 型号（规格）四种载体彼此不连通

    根因：现象、码、部件、型号/规格、章节各自成表，查询时临时拼接

    • 工单本体（Ontology）：用业务语言定义 RepairObject / Fault / AlarmCode(FaultCode) / RepairAction / Part / Technician / WorkOrder / ManualSection，并提前固化关联（型号/规格↔手册版本↔章节、现象↔码↔部件、订单↔备件↔技师） 同族复用 · 通用"制造/服务/巡检"对象模型；换行业只换实体名
    • 主数据统一编码：料号、报警码/故障码、手册章节号、型号/规格配置各给唯一 ID 与版本；变更有生效日期 同族复用 · 备件主数据、设备台账、固定资产编码统一
    • 型号/规格约束强制校验：任何检索与建议都必须带型号/规格/配置过滤；无匹配则明确说"无手册依据"，不猜 同族复用 · 多规格多配置产品的选型与报价防错
  • L2-3现场输入的口径与知识库口径对不上

    根因：技师说"起步发闷"，码表写"P0AA6"，手册写"驱动系统功率限制"（设备侧同理：口语现象 / 报警码 / 手册描述三套说法）

    • 现象 ↔ 报警码/故障码映射表：人工维护主干（码 → 标准现象描述），从历史工单反向挖掘补充同义映射；技师输入先做症状归一化再进检索 同族复用 · 客服工单分类、售后问诊分流、设备报警代码归一
    • 检索双过滤 + 混合召回：结构化过滤（型号/规格/码域）+ 语义召回（手册语言）+ 关键词召回（料号/码）三路并集后重排 同族复用 · 法规/标准/合同条款检索
  • L2-4派工与技师能力没有数据化

    根因：靠班长对"谁熟哪型号、哪类故障"的记忆

    • 技师技能画像：从历史工单反推每名技师的"擅长故障域 × 熟悉型号/规格 × 认证资质 × 通过率" 同族复用 · 岗位胜任力画像、招聘匹配、外包队伍能力评估
    • 派工匹配打分 + 理由生成：得分 = 技能匹配 + 故障域重合 + 班次可用 + 资质合规，输出 Top-N 与选他/不选他的理由 同族复用 · 抢单派单、值班排班、维修工程师分派
  • 横贯 回写闭环 + 闭环即评测

    跨 L2 的横贯机制

    • 回写闭环 + 闭环即评测：技师勾选执行的步骤与最终原因回写工单；每条闭环工单自动成为评测样本；误判案例回流为 few-shot 与规则修正 同族复用 · 所有"人在回路"的 AI 系统通用：合同审核、质检判定、客服工单

蓝莓种植的每一步，能不能都有据可查？

  • L2-1农事记录没有对象化，"标准"落不到现场动作上

    根因：记录形态是"地块 + 日期 + 一句话"，没有品种/生育期/行/株/农事批次/采收批次这些对象，标准条款挂不到具体动作上。

    • 农事本体（Ontology 三步法）：Farm·Block·Row·Bush·Operation·Input·HarvestBatch·Quality·Clause，Links 提前固化 同族复用 · 通用"种植/养护"对象模型（设备/模具/批次/客户同一套结构）
    • 标准条款 → 可勾选作业项：把《蓝莓栽培技术规范》拆成有对象、有触发条件、有判定依据的作业项，条款原文与判定口径一起入库 同族复用 · 施工工艺卡 · 检验规程 · EHS 检查项 · 内审条款
    • 确认式采集（拍照 + 一句话）：ASR+VLM 抽草稿 → 农工只做确认/改 → 低置信高亮 → 写入对象 同族复用 · 巡检打卡 · 仓储收货 · 实验记录 · 设备点检
  • L2-2投入品是不可核的黑箱

    根因：农药/肥料/水的信息只存在于包装标签照片里，登记证号、成分、剂量、禁限用属性没有落成可比对的字段。

    • 投入品主数据 + 包装标签 OCR 管线：读产品名/成分/登记证号/剂量 → 映射主数据，禁限用属性人工确认 同族复用 · 材质质保书 · 危化品 SDS · 兽药疫苗 · 试剂耗材
    • 合规规则引擎（禁限用 + 安全间隔期）：规则来自官方清单与农艺师，模型不得臆造，录入即校验 同族复用 · 药/证/票/危化品/超期资质等硬约束场景
    • 投入品—采收批次关联台账：采收批次反向展开"采前 N 天内的全部投入品" 同族复用 · 农残速测异常溯源 · 追溯召回范围圈定
  • L2-3技术指导与培训交付过程没有留痕

    根因：品种推荐、栽培方案、建园指导、田间学校授课是这家单位的"产品"，但交付给谁、给了什么、覆盖多少面积、结果如何，几乎没有记录。

    • 技术指导交付记录：指导对象/方式/交付物/面积与株数/交付人 同族复用 · 设备维保商技术服务单 · 顾问工单 · 检测委托单
    • 培训场次台账：课次/学员名单与人数/教材版本/签到/考核结果 同族复用 · 企业内训 · 农机校 · 职业院校课程记录
    • 指导闭环与复访回流：按节点回访成活率/产量/品质，结论回流修订方案与教材 同族复用 · 售后回访 · 慢病随访 · 会员复购跟进
  • L2-4农事与品质、成效指标不在同一时间轴上

    根因：糖度、硬度、商品率波动时无法定位到某次施氮、打药或灌溉；示范区的亩产/增产/辐射面积/培训人次散在不同报表里。

    • 植株/批次级时序视图：农事、投入品、品质指标落在同一时间轴上 同族复用 · 通用"资产时序档案"：设备履历 · 批次质量谱 · 客户跟进史
    • 相关性归因提示（只提示不下结论）：同期共现 + 相关性，输出"可能相关 + 样本量 + 区间" 同族复用 · 工单与返修 · 巡检与故障 · 投放与转化
    • 成效指标台账：亩产/增产/辐射面积/培训人次/种苗销量统一口径，可按品种·区域·年度对比 同族复用 · 项目后评价 · 示范区验收 · 专项资金绩效报告

场景：记录散在纸本和微信群

修剪、疏果、施肥、灌溉、打药、采收——这些操作决定了糖度、硬度和商品率，但记录散在纸本、微信群照片和各自 Excel 里。品质一波动，就查不到是第几次施氮、哪一天打药导致的。

  • 农工不愿填表：15 分钟/条，且看不到用在哪
  • 颗粒度太粗：多数只到地块级，真追溯要到行/株
  • 照片没法用：药名、剂量、登记证号都在像素里
  • 认证要材料来不及：追溯报告只能翻本子拼

结项要交什么

训练营官方口径：实战收获 = 真实卡顿 · 团队 AI 模型 · 测试与验证记录。结项交的是可验证的 AI 原型，不是 PPT。

真实卡顿

每题记录 2 次实际踩坑：数据格式、接口、口径、模型失败样本。这是训练营明确要求的第一项产出。

团队 AI 模型

不是"我们用了大模型"，而是带评测集的模型：回测脚本 + 评测集入库，跑得出分数。

测试与验证记录

甲方人工抽检表、断言报告、干预演示记录——每条建议"可用/需改/不可用"由甲方签字。

可复用件

每题标出哪些沉淀成通用件。碎石路修成高速公路，是 FDE 模式能规模化的前提。

三条贯穿六题的硬规矩：① 模型不做算术、不编事实，凡是要签字的数字与参数都必须可溯源； ② 低置信度结果必须走人工确认台，自动化率再高也不取消这一步； ③ 每题都有护栏指标（不恶化 / 零违反 / 不超基线），只报好看的那条不算达标。
